## A. 构建与工程结构

### A-1【高】CMakeLists 固件目标漏编 `esp_link.c`，按 README 走 CMake 交叉编译必然链接失败
- 位置：`CMakeLists.txt:41-75`（`add_executable(bionic_fish.elf ...)` 源列表），对照 `app/Src/app.c:64/187/239/353` 大量调用 `EspLink_*`
- 事实：固件目标源列表含 bsp_board/bsp_time/bsp_uart，**唯独没有 `bsp/Src/esp_link.c`**；而 `EspLink_Init/Send/Poll/RxOverflow/Service` 等只在 esp_link.c 中定义。host-test 目标不引用 EspLink，所以默认 `ON` 的主机测试全绿，掩盖了固件目标的问题。
- 旁证：已交付 `build-firmware/bionic_fish.bin` 是用 `scripts/build_firmware_direct.sh` 构建的，**该脚本的 `REPO_SRCS` 里明确包含 `bsp/Src/esp_link.c`**——两条构建路径的源列表已漂移。
- 影响：任何人按 README §“STM32 交叉编译”执行 CMake 路径，链接阶段报 `undefined reference to EspLink_*`。
- 修复：在 CMakeLists 固件源列表补入 `bsp/Src/esp_link.c`。

### A-2【高】交付的 `stm32f1xx_hal_conf.h` 缺失 `assert_param` 定义，任何“原样编译 HAL”的路径都会编译失败
- 位置：`Core/Inc/stm32f1xx_hal_conf.h`（全文 0 处 `assert_param`）；HAL 库每个源文件无条件调用 `assert_param(...)`
- 事实：标准 CubeMX 生成的 hal_conf 末尾必有 `#ifdef USE_FULL_ASSERT ... #else #define assert_param(expr) ((void)0U) #endif`，本工程被精简掉了。直连脚本因此被迫用 `-include build-firmware/assert_param.h` 注入空定义（`scripts/build_firmware_direct.sh:16-21` 及注释），并已把 hack 产物留在 `build-firmware/assert_param.h`。
- 影响：CubeIDE/CMake 从零构建（CMake 固件目标没有该 -include）都会在编译 HAL 源时失败。已交付 bin 能出来只是因为走了带 hack 的直连脚本。
- 修复：把 `assert_param` 空定义补回 hal_conf（或在 CMakeLists 增加同样的强制 include 并写入脚本说明），并删掉两套构建对 hack 的不对称依赖。

### A-3【中】构建路径三套并存且相互漂移，已交付 bin 不可按文档复现
- 位置：`README.md`（“STM32 交叉编译”只写 CMake 通用路径）vs `scripts/README.md`（只讲 flash）vs `scripts/build_firmware_direct.sh`（从未被文档提及，却是产出 bin 的真实路径）
- 事实：直连脚本硬编码本机绝对路径：`/c/Users/CloudyRain/STM32Cube/Repository/STM32Cube_FW_F1_V1.8.7`、`D:/STM32CubeIDE_1.19.0/...`、Arm gcc 13.3.1（与 `build-firmware/bionic_fish.map` 头部记录一致）；且其使用的 CubeF1 是 **V1.8.7**，而 `bionic_fish.ioc` 记录 `ProjectManager.FirmwarePackage=STM32Cube FW_F1 V1.8.6`。
- 影响：换机器/换版本无法一键复现交付 bin；文档口径与实际构建源不一致。
- 修复：在 README/scripts README 明确 `build_firmware_direct.sh` 是“本交付 bin 的实际构建脚本”，写明需替换的路径常量；统一 CubeF1 小版本口径（V1.8.6 vs V1.8.7）。

## B. 通信 / 协议 / 链路层

### B-1【高】`通信协议.md` §5 承诺的“UART 级丢字节（环形缓冲满 / ORE）立即安全断链并回 E_RX_OVERFLOW”**从未在代码接线**
- 位置：`bsp/Inc/bsp_uart.h:18-20`、`bsp/Src/bsp_uart.c:110-137,144-157`、`app/Src/app.c:187-205`；对照 `通信协议.md:55,80-81,125-133`
- 事实：
  - `BSP_Uart_OnRxComplete` 重挂失败、`BSP_Uart_OnError`（ORE）、`RingBuffer_PushFromIsr` 满时都会置 `s_esp_rx.data_lost = true`，`overflow_count++`；
  - 但 `BSP_Uart_EspRxLost()` / `BSP_Uart_EspRxOverflowCount()` **定义了却没有任何调用方**（全工程 grep 仅定义处）；
  - `app.c:187` 只检查 `EspLink_RxOverflow()`——那是 esp_link **软件 phone 缓冲**（256B）的溢出，不是 UART 环形缓冲(256B)或硬件 ORE。
- 影响：主循环被软 I2C/OLED 忙等拖住时，UART 环满丢字节无痕；ORE 丢字节只置位无人消费。**残缺字节可能被拼成一条恰好语法合法、语义合法的 CMD 被接受执行**——这正是协议文档承诺要防的“半真半假命令”。`BF_FAULT_ESP_RX_LOST`（bit1）文档语义为“UART 溢出/ORE 丢字节”，实际只在软件缓冲溢出时置位，语义错位。
- 修复：在 `ServiceProtocol` 顶部把 `BSP_Uart_EspRxLost()` 与 `L.rx_overflow` 同等对待：排空残留 → `Protocol_Reset` → `Control_ForceDisconnect` → `Motor_ApplyFailsafe` →（按配置回中）→ 回 `E_RX_OVERFLOW` → `BSP_Uart_ClearEspRxLost()`。

### B-2【高】esp_link 的 `+IPD` 解码状态机可被异常帧长/截断**永久卡死**，溢出清除也救不回
- 位置：`bsp/Src/esp_link.c:130-153`（`RX_IPD_LEN` 中 `ipd_len` 无限累加；`RX_IPD_DATA` 无兜底）、`esp_link.c:199-202`（`ClearRxOverflow` 只清标志）、`app.c:194`
- 事实：`+IPD,<id>,<len>:` 的 len 是**无上限 uint32 累加**。若 ESP 报文被截断（客户端中途断开）、或 len 巨大、或 `':'` 始终不出现，状态机停在 `RX_IPD_DATA`/`RX_IPD_LEN`，把后续**所有真实帧字节当幻影帧载荷吞掉**。`rx_overflow` 触发后 app 清标志并复位协议/会话，但**没有把 `L.rx` 复位到 `RX_IDLE`**——吞字节继续，标志被再次置位，形成“每次 ServiceProtocol 都进溢出分支”的死循环式链路瘫痪（直到幻影 len 被真实流量凑满才偶然恢复）。
- 修复：① `ipd_len` 设合理上限（如 `4×CFG_PROTOCOL_PAYLOAD_MAX`），超限即复位；② `ClearRxOverflow` 顺带 `L.rx = RX_IDLE; L.ipd_len = 0; L.ipd_got = 0;` 并把 phone 缓冲内残留置为无效；③ 在 `RX_IPD_DATA` 加字节间隔超时看门狗，超时强制回 `RX_IDLE`。

### B-3【中】下行 CIPSEND 无握手、无重试，三次独立入队不原子 → 可撕裂帧、ESP 端悬挂
- 位置：`bsp/Src/esp_link.c:204-216`（`SendQueuedFrame` 三次调用 `RawCstr/BSP_Uart_SendEsp`，返回全部忽略）、`bsp/Src/bsp_uart.c:47-61`（队列满即丢）
- 事实：`AT+CIPSEND=0,<len>` 头、帧体、`\r\n` 分三次入同一 512B 串口 TX 队列，**中间若队列满，只有部分字节发出** → ESP 收到 CIPSEND 头却等不到足量载荷（等待/超时后 `SEND FAIL`），后续被发的下一条 `AT+CIPSEND` 会被当载荷吞掉，形成串行错乱链。代码也不等 ESP 的 `>` 提示、不解析 `SEND OK/ERROR/link is not valid`（非 `+IPD` 行全部只喂给 `OK` 判断）。
- 影响：主要出现在串口 TX 队列拥塞或 ESP 客户端断开瞬间；对即时 ACK/ERR 是**不可弥补的丢帧**。
- 修复：三个入队调用改为检查返回并整体失败即回滚/重试；或引入下行状态机（发头 → 等 `>` → 发体 → 等 `SEND OK`）；至少让 `slots` 满时的处理不撕裂串口序列。

### B-4【中】ACK/ERR 与周期 STA 同权排队、满即丢且无事件级重传
- 位置：`bsp/Src/bsp_uart.c:47-61`、`app/Src/app.c:62-87`（Broadcast）、`esp_link.c:33`（slots=4/冷却 150ms）
- 事实：`EspLink_Send` 满则返回 false，`Broadcast` 只置 `BF_FAULT_UART_TX_DROPPED`。ACK/ERR 是“一帧一个语义”的事件性应答（如 `E_STEPPER_HW_UNCONFIRMED`、`E_RANGE`），丢了上位机就可能**误判命令已被接受并继续下一步**；STA 丢了 200ms 后自然重发，二者不应同权。
- 修复：ACK/ERR 走更高优先级槽位（可挤掉队尾未发出的旧 STA），或满时保留最新事件帧并丢最旧。

### B-5【低】组帧/失联超时（250ms/1000ms）对主循环节拍敏感，缺乏硬调度保证
- 位置：`app/Src/app.c:165-220`（帧超时按主循环轮询字节时间戳判定）、`app.c:253-302`（`OledBringUp` 忙等最长约 8×100ms＋扫描探测，`I2cScanDebug` 约 112 次探测）
- 事实：初始化期间 ~1s 级忙等窗口内 ESP 持续来字节会灌满 256B UART 环（约 22ms 即满）——与 B-1 叠加是启动即丢帧的主要温床。运行期每条软 I2C 事务是 μs~ms 级忙等，但每轮只做一项 OLED 工作，理论上不会持续 >250ms 停摆（OledBringUp 只在启动），故运行期风险中等偏低，但**没有 IWDG/任务超时兜底**。
- 建议：初始化忙等期间暂停订阅/清空链路，结束进环前 `RingBuffer_Reset`；或在 README“运行边界”明确该启动窗口行为。

## C. 控制与应用层

### C-1【高】每个“内容相同、seq 前进”的重复命令都会把步进换相时钟拨回 now → 相位被提前截断、实际转速偏高且抖动
- 位置：`app/Src/app.c:130-131`（每个新命令都 `Motor_ApplyCommand`）→ `control/Src/motor_control.c:92`（`next_commutation_us = now_us`）
- 事实：只有同 seq 同载荷才走 DUP 分支（不重排时钟）；**seq+1 的同载荷刷新命令**（心跳/重发、舵机微调时连带）每次到达都会让 `Motor_Service` 在下一个主循环立刻多换一相，把“进行中相位”的驻留时间从最大一个周期压到几 ms。若上位机以 <1s（保活 1000ms 要求）周期刷新，则稳态换相速率 = 额定 + 刷新率×(每命令一相)，**实际转速高于指令值且不确定**。
- 影响：60/100 RPM 两档名义速度在真实链路下偏快/抖动；在未确认参数阶段不易察觉（门禁未开），一旦确认参数通电可能表现为转速超预期。
- 修复：`Motor_ApplyCommand` 改为“幂等不重排”：仅当 move/rpm 相对上次变化（或当前停转）时才重排 `next_commutation_us`；同目标重复命令只刷新保活，不动换相时钟。

### C-2【中】步进参数门禁缺少上限/溢出防护：配置错误会“静默停转”或给出错误转速，且无任何故障位
- 位置：`app/Inc/app_config.h:125-129`（只校验非 0）vs `control/Src/motor_control.c:31-35`（`denominator = rpm × comm` 无界 32 位乘法）
- 事实：`CFG_STEPPER_COMMUTATIONS_PER_OUTPUT_REV` 无上限检查：乘积溢出 → `denominator` 回绕成小值 → 错误的高换相频率；`denominator > 60e6` 时 `period_us` 截断为 0 → `StopStepper` **静默停转**——命令已被 ACK、`step_running` 却为 false，无 `BF_FAULT`。同期也没有“每输出转换相数 × 60/100 rpm 产生的最低驻留时间须大于代码开销”的编译期/启动期检查。
- 修复：为 comm 增加合理范围（如 4..20000）的 `#if` 校验；`StepPeriodUs` 结果做饱和与 0 判定并置 `BF_FAULT_CONFIGURATION`；在确认参数的门禁通过时打印/上报实际算出的周期。

### C-3【中】三个物理按键（KEY1/KEY2/KEY3）零消费、无去抖，.ioc 名称与真实配置矛盾
- 位置：`bsp/Src/bsp_board.c:142-161`（`BSP_ButtonPressed` 定义）— 全工程**无任何调用方**；`Core/Src/gpio.c:37-45`（普通 `GPIO_MODE_INPUT` + 上拉）；`bionic_fish.ioc`（KEY3 PA8 写 `GPIO_ModeDefaultEXTI`，名称暗示外部中断）；`app_config.h:35` `CFG_BUTTON_DEBOUNCE_MS` 无使用者
- 影响：若任一键本意是本地急停/安全功能，则当前固件该功能**完全失效**（安全只能靠链路）；即使只是预留，也是“物理硬件存在但软件死代码 + 配置名称误导”。README/交付说明均未声明按键用途。
- 修复：要么明确删除按键接口与 .ioc 的 EXTI 字样（改普通输入描述）；要么在 `App_Process` 接入按键功能（含按 `CFG_BUTTON_DEBOUNCE_MS` 去抖），并在文档写明每个键的动作。

### C-4【低】PC13 快闪/慢闪诊断语义（OLED 是否起来）只在代码里，文档/验收清单未写明
- 位置：`app/Src/app.c:377-381`（`s_oled_ok ? 500ms : 120ms`）
- 事实：代码用闪烁频率区分 OLED 初始化成败（快闪=没认到屏），README“首次上电”与 `验收检查清单.md` 都只让“观察 PC13”，未解释判别规则。
- 修复：README/验收清单补一句：“PC13 快闪（约 120ms）＝OLED 初始化失败；慢闪（约 500ms）＝正常”。

## D. 驱动与底层

### D-1【中】OLED 半途刷屏失败后的恢复链路偏脆弱；上电首次失败后**永不重试**（黑屏 + 只能靠快闪诊断）
- 位置：`drivers/Src/ssd1306.c:190-240`、`app/Src/app.c:253-278`（`OledBringUp`）、`oled_ui.c:61-71`
- 事实：复核结论——运行期单次失败后 `refresh_active=false → IsIdle=true`，下一轮 `OledUi_Update`（200ms 后且空闲）会整帧重画，**能自愈**，但整帧从页 0 重发、无断点续传；`i2c_error_active` 只在完整一帧成功后清除，期间 app 每轮置 `BF_FAULT_OLED_I2C`，故障位会随刷屏节奏闪烁。真正缺口在**上电路径**：`OledBringUp` 只在 `App_Init` 尝试（8 轮 × 每次失败等 100ms），之后永不再尝试；屏在复位窗口未就绪 = 整机工作期间黑屏，只能靠快闪诊断，无后台重试。
- 修复：把 OLED 重试并入运行期 Service（如每 1~2s 在 fault 置位且 idle 时重新 Probe/Init），而不是只在启动试一次。

### D-2【中】USART3 只配 TX 却按 TX_RX 初始化且无 RX 缓冲/错误恢复，调试口方向理解易错
- 位置：`bsp/Src/bsp_uart.c:99`（只对 huart2 开 `HAL_UART_Receive_IT`）、`bsp_uart.c:130-137`（`BSP_Uart_OnError` 只处理 huart2）、`Core/Src/usart.c:15`（`UART_MODE_TX_RX`）
- 事实：CH340N 回发（PB11）没有接收缓冲、没有重挂、没有消费；若有人往调试口发命令/回显，字节进不了固件，且 ORE 语义没有处理分支（HAL 层仍会清标志，不会锁死，但表现为“发了没反应”）。
- 修复：明确 `huart3` 为 `UART_MODE_TX`（或补 Receive_IT + 消费路径），并在文档写明“调试口仅输出”。

### D-3【中】JY61P 连续失败后旧姿态仍参与“合理性”比较 → 失效恢复后的首个有效样本可能被误杀
- 位置：`drivers/Src/jy61p.c:83-116`
- 事实：I2C 失败时保留旧数值仅置 `valid=false`（注释说明用意是“旧值不伪装实时”）；但下次成功读取后 `IsPlausible` 仍拿这个**很久以前的旧值**与候选值比较，鱼体若在断链期间大幅运动，新样本会被误判 SAMPLE_INVALID，失败计数继续累加（3 次又触发一次 BusRecover+Probe）。系统能自愈，但首次恢复会额外多失败几次、故障位抖动。
- 修复：合理性比较在 `!old_value->valid` 时直接放行即可（代码 34-35 行已有该分支，但 invalid 后旧数值没被清——建议 invalidate 时同时把姿态数值归零或保留 `last_update_ms` 判断新鲜度）。

### D-4【低】TIM2 coast 语义依赖“CCR 可安全大于 ARR（=100% 恒高）”的 F1 未文档化行为
- 位置：`bsp/Src/bsp_board.c:9-16`（`PercentToCompare` 上限 100 → `CCR=period=3600 > ARR=3599`）、`bsp_board.c:119-129`（Coast 置 CCR=100%）
- 事实：F103 比较器对 CCR>ARR 永不匹配 → 输出恒高，与 IN1=IN2=低共同构成 TB6612 coast。逻辑自洽且安全，但这是**依赖硬件行为的隐性约定**：若有人把 Coast 实现改成“PWM=0”，会从 coast 变成文档注释里明确警告过的非 coast 态（`bsp_board.c:80-82`）。建议加显式注释/`assert(CCR<=ARR+1)`，说明“coast 必须 IN=低+PWM=高”。

### D-5【低】软件 I²C 强依赖“外部 3.3V 上拉已接”与 5µs 半周期参数，总线被强拉死时恢复能力有限
- 位置：`drivers/Src/soft_i2c.c:201-221`、`Core/Src/gpio.c:31-35`、`app_config.h:58-64`
- 事实：OD 输出 + 无内部上拉；若上拉缺失/接错 5V，所有读采样浮空（代码无法自检，只能靠 `I2CSCAN` 启动打印间接判断——这个打印设计是对的，值得写进文档）；`BusRecover` 对“从机强拉低”只能 9 脉冲后超时放弃。文档已标“待实测”，此处仅建议把 `I2CSCAN` 输出补进 README 故障排查章节。

### D-6【低】`Ssd1306_Init` 内 `memset(display,0)` 之后地址/总线重设，若 `SoftI2c_Probe` 失败会留下 `i2c_failures++` 但 OledBringUp 换地址重试会重复计数——无功能影响，仅供诊断计数语义注明。

## E. 文档一致性（除 B-1/E 外跨交付包问题）

### E-1【高】ESP 桥接“双层交付”互相矛盾：固件是 AT/TCP 方案，配套文件夹却教人刷无 AT 的自定义透传桥
- 位置：`bsp/Src/esp_link.c:4-11,208,230-233`（发 `ATE0/CIPMUX=1/CIPSERVER=1,9000/AT+CIPSEND`、解析 `+IPD`，要求**出厂 AT 固件 + TCP**）vs `ESP01S_AP_UDP_Bridge/README.md`（“STM32 固件**不需要任何改动**”）与 `ESP01S_AP_UDP_Bridge.ino`/`ESP01S_TCP_Transparent_Bridge.ino`（无 AT 的 UDP/TCP 透明字节管道，UART 是干净管道，`+IPD`/CIPSEND 不存在）

- 修复：在 `ESP01S_AP_UDP_Bridge/README.md` 顶部加显著告警：**本桥仅当固件未采用 esp_link.c 的 AT 驱动时可用；当前交付固件 = AT + TCP（CIPSERVER=1,9000），请保持 ESP 出厂 AT 固件，勿刷本目录固件**；或在交付口径中收敛出唯一放行形态。

## F. 复核后判定为“设计自洽 / 非缺陷”的排查点（防止误改）

以下各项经我逐条重读确认**不是问题**，修改前请三思：

1. **时钟树**：HSE 8MHz ×9 → 72MHz；APB1=36MHz（F1 定时器×2=72MHz）。TIM2 PSC0/ARR3599=20kHz ✓；TIM3 PSC71/ARR19999=50Hz 且 **1 count=1µs**（CCR 即脉宽 us）✓；TIM4 PSC71/ARR65535=1MHz 时基，`BSP_Micros` 的双读护栏正确 ✓。静态 `#if` 校验（app_config.h:103-129）与实际值全部通过。
2. **步进换相数学**：`60e6/(rpm×comm)` 量纲正确（60 s/min × 1e6 µs/s），与 TIM2 20kHz 无关（相位驻留由 TIM4 微秒时基调度，属软件换相设计）✓；`(step_phase - 1U) & 0x03U` 在 phase=0 时经无符号提升回绕到 3，反向换相正确 ✓；四拍表顺序与 reverse 异或逻辑自洽 ✓。
3. **序号窗口**：`delta∈[1,0x7FFF]` 新帧、`0x8000` 歧义拒绝、`>0x8000` 旧帧；超时/溢出清 `sequence_valid` 允许重链 ✓（host 测试已覆盖回绕，`protocol_host_test.c:101-124` 通过）。
4. **SPSC 无锁环形缓冲**：ISR 单写 head、主循环单写 tail、2 的幂门禁、留一槽判满——正确。
5. **TIM2 CCR=100%（=ARR+1）→ 恒高 = coast 前提**：见 D-4，行为本身安全。
6. **复位初始安全态**：`gpio.c:13-18` 先写电平再配输出（AIN/BIN 低、LED 灭、I²C 释放），TIM3 启动前 CCR 已预置 1500（`tim.c:47`）→ 舵机无启动毛刺 ✓。
7. **NVIC/中断**：分组 4、USART2=1 / TIM4=2 / USART3=2 与 .ioc 一致；中断只做入队/重挂，无阻塞业务 ✓。
8. **`step_running=true` 时 PWM 0% 不动**（`CFG_STEPPER_WINDING_PWM_PERCENT=0` 门禁）：这是**设计**——参数未确认前拒绝励磁并置 `BF_FAULT_STEPPER_HW_UNCONFIRMED`，不是 bug（README 已明示）。
9. **`move=S` 仍要求 step_speed/servo/turn 合法且字段全齐**：协议表明确约定，属设计。
10. **STBY 无 STM32 控制脚**：代码注释与三份文档一致承认这是硬件失效保护缺口，等待实测——不是代码漏项，但**是上电前的真实硬件待办**（务必保证 STBY 被可靠拉高）。
