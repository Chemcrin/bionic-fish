# 安卓端改造方案：双电机控制 + 舵机行程 ±15°（目标 v0.5.0）

> **本文取代** 同目录下的 `双电机控制与舵机20度_安卓端改造方案.md`（那份写的是 ±20°，已过期）。
> **适用对象**：`仿生鱼安卓_v0.4.0_交付包/Android工程`（当前 `versionName 0.4.0` / `versionCode 6`）
> **建议目标版本**：`versionName 0.5.0` / `versionCode 7`
> **本轮仍只出方案，不改安卓源码。**
>
> 本文与固件源码逐条对应；所有行号均已实机核对过。

---

## 0. 一句话结论

安卓端要做三件事：

1. **协议层**：CMD 增加可选字段 `m2=`；STA 增加可选字段 `m1=` / `m2=`；**舵角上限由 30° 改为 15°**。
2. **UI 层**：操控台新增 M2 一组「前进 / 停止 / 后退」；舵机预设按钮与滑块刻度由 ±30° 改为 **±15°**（滑块 `steps` 同步由 59 改 29）。
3. **安全层**：安全停止必须**同时停两路**；反向开关的默认值需要放开。

## 1. 固件侧新增内容（事实基线，勿凭记忆改）

### 1.1 推进执行器换代：步进 → 两路直流减速电机

| 项目 | 变化 |
| --- | --- |
| 执行器 | 原「42 两相双极步进 + TB6612 双桥软件四拍换相」→ **M1 = 370 直流减速电机**（A 桥）、**M2 = N20 直流减速电机（12V 版）**（B 桥） |
| 换相 | 换相表、相序、每转步数、RPM 换算、换相周期**全部删除**；启停与换向只由 `IN1/IN2` 决定 |
| PWM 载波 | TIM2 周期由 20 kHz 改为 **2 s**（`CFG_MOTOR_TIM_PRESCALER=7199` / `CFG_MOTOR_TIM_PERIOD=19999`）。**原因见 1.1.1** |
| 占空比 | 两路共用同一挡位：**满速挡 95%**（`CFG_MOTOR_FULL_DUTY_PERCENT`）/ **低速挡 60%**（`CFG_MOTOR_LOW_DUTY_PERCENT`）。不再有各自的编译期固定值，`CFG_MOTOR_A/B_DUTY_PERCENT` 仅作可选覆盖 |
| 调速 | **上位机只能选挡位，不能连续调速。** 字段 `step_speed=60/100` 仍必填、仍校验取值，现在映射为占空比挡位：`100`→满速挡、`60`→低速挡 |
| 反馈 | 无编码器、无闭速、无位置闭环。`step_rpm` / `step_est` / `step_actual` 恒为 `NA` |

> ⚠️ 安卓端不要再把它当成"可调速的步进"来设计 UI。`step_speed` 不是历史废字段，而是**挡位选择器**——安卓端若要暴露"低速挡"，就发 `step_speed=60`，其余情况发 `100`。

#### 1.1.1 为什么改成「2 s 慢周期 + 95% 占空比」

2026-09-23 现场问题是：**VM = 12 V、TB6612 的 STBY 已接高，电机却带不动负载**。

根因是原 100% 占空比在 STM32F1 上落成 `CCR = ARR + 1`，TIM2 比较输出**恒为高、永不翻转**；而 TB6612 的 PWM 输入需要持续的开关边沿维持高侧栅极/自举驱动。恒定高电平使自举电容得不到刷新，高侧无法持续导通 → 驱动能力弱，带载即掉。

处置是两条一起上：**满速挡降到 95%**（保证每个周期有一次完整低电平沿；95% × 12 V = 11.4 V，转速扭矩几乎无损），**载波周期拉到 2 s**（用户要求"2 s 一周期、满速满扭驱动"，也便于用示波器直接观察边沿）。

> **这对安卓端没有协议影响**——安卓侧只发 `step_speed`，具体占空比由固件决定。但**文案要改**：`step_speed` 应描述为"满速挡 / 低速挡"，不要再写"不改变输出的兼容字段"。

### 1.2 CMD（安卓 → 固件）：新增可选字段 `m2`

```
<CMD,seq=12,move=F,turn=L,step_speed=60,servo=-15,m2=R>\n
```

| 字段 | 取值 | 必填 | 语义 |
| --- | --- | --- | --- |
| `seq` | `0`~`65535` | 是 | 序号窗口；`last_sequence + 1` 永远合法 |
| `move` | `F` / `R` / `S` | 是 | **M1（370 主推进）** 前进 / 后退 / 停止 |
| `turn` | `L` / `R` / `C` | 是 | 舵机方向语义，必须与 `servo` 符号一致（负=L、0=C、正=R） |
| `step_speed` | `60` / `100` | 是 | **占空比挡位选择器**：`100` = 满速挡（固件 95%）、`60` = 低速挡（固件 60%）；两路共用同一挡位 |
| `servo` | `-15`~`15` | 是 | 舵机目标角；**越界由固件回 `E_RANGE` 整条拒绝**（不夹紧） |
| `m2` | `F` / `R` / `S` | **否** | **M2（N20）** 前进 / 后退 / 停止；**缺省 = 停止** |

关键语义（三条都必须理解，否则会做出错误的 UI）：

1. **`m2` 缺省是"停止"，不是"保持不变"。** 固件在解析层**显式**写了 `command.m2 = BF_MOVE_STOP;`（`protocol/Src/ascii_protocol.c:117-119`）。原因很实在：`BF_MOVE_FORWARD` 的枚举值恰好是 `0`，如果依赖 `memset` 清零，老客户端不发 `m2` 时会被当成"**M2 前进**"。
2. **整条命令是一个完整目标，没有增量语义。** 每个被接受的 CMD 会同时决定 `M1`、`M2`、舵机三者。**安卓端每帧都必须把想保持的状态一并带上**——这就是 `m2` 缺省取"停止"的根本原因。
3. **`move=R` 已放开。** 以前会回 `E_STEP_REVERSE_UNSUPPORTED`，现在正常接受并真正驱动 A 桥反转。

### 1.3 STA（固件 → 安卓）：新增 `m1` / `m2`

```
<STA,seq=12,link=1,step_rpm=NA,step_est=NA,step_actual=NA,step_on=1,servo=-15,
     roll=1.2,pitch=-2.4,yaw=85.7,m1=F,m2=R,err=0>\n
```

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `step_rpm` / `step_est` / `step_actual` | 恒为 `NA` | 语义不变，仍表示"固件不声明转速" |
| `step_on` | `0` / `1` | **语义已收窄：表示 M1 是否在运行**，恒等于 `(m1 != S)`。**不代表 M2** |
| `servo` | `-15`~`15` | 当前舵角（限幅后的命令值，不是实际舵面反馈角） |
| `roll` / `pitch` / `yaw` | 数字或 `NA` | 不变 |
| `m1` | `F` / `R` / `S` | **新增**：M1 当前已下达方向；停止为 `S` |
| `m2` | `F` / `R` / `S` | **新增**：M2 当前已下达方向；停止为 `S` |
| `err` | 十进制位图 | 位定义不变 |

**兼容性要点**：`m1` / `m2` 是**追加**在 `err` **之前**的字段，v0.4.0 的全部字段原样保留、**位置也未变**。所以：

- 安卓解析器的 `required` 集合**必须保持原样 10 项**，**不要**把 `m1`/`m2` 加进去 —— 一旦加进去，连旧固件时 STA 会被判成 `MISSING_FIELD`，兼容性立刻破裂。
- `m1`/`m2` 缺失（旧固件）时按 `null` 处理，UI 显示"未知"而不是报错。
- **`step_on` 只反映 M1。** 要在界面上表达"哪一路在动"，必须自己从 `m1` / `m2` 推导，不能只看 `step_on`。

### 1.4 失联与安全语义

- **1000 ms 内没有有效 CMD**（含同序号幂等重传）→ **两路电机同时 coast**（M1、M2 都停），舵机按配置回中，并主动关闭旧 TCP。
- UART 丢字节、TCP 断开、发送事务失败会更早触发同一套停止处理。
- 非法 `m2` 值（如 `m2=X`）→ 回 `E_RANGE`，**整条命令被拒，且不改动任何执行器**。
- `m2` 字段重复出现 → `E_DUP_FIELD`。

### 1.5 舵机行程：±30° → ±20° → **±15°（本次变更）**

固件把"能转多远"（`CFG_SERVO_SAFE_MIN/MAX_DEG`）与"多少度对应满脉宽"（`CFG_SERVO_FULL_SCALE_DEG`）拆成了两个独立参数：

```c
/* app/Inc/app_config.h */
#define CFG_SERVO_FULL_SCALE_DEG   30     /* 换算基准：1000–2000 µs 名义对应 ±30° */
#define CFG_SERVO_SAFE_MIN_DEG     (-15)  /* ← 本次由 -20 改到 -15 */
#define CFG_SERVO_SAFE_MAX_DEG     15     /* ← 本次由  20 改到  15 */
```

这个拆分很重要：**收窄 `SAFE_*` 不是把 15° 撑满 1000–2000 µs，而是只给出满量程的 1/2 脉宽偏移**。所以机械转角是真的变小了，而不是只把标签从 30 改成 15。

## 2. 舵机 ±15° 的换算与跨端一致性

### 2.1 固件实际换算式（`control/Src/servo_control.c:17-41`）

中心 1500 µs，满量程 ±500 µs 对应 ±`FULL_SCALE_DEG`：

```
offset_us = 500 × |angle| / 30          （整数运算，向下取整）
（极性在 2026-09-11 已对调：请求角先取反再换算）
左舵（请求负角） → 1500 + offset
右舵（请求正角） → 1500 − offset
中位            → 1500
```

### 2.2 三代行程的脉宽对照（`FULL_SCALE_DEG` 始终为 30）

| 请求角 | 行程版本 | `offset` | 实际脉宽 | 说明 |
| --- | --- | --- | --- | --- |
| `0°` | 全部 | 0 | **1500 µs** | 中位不变 |
| `−15°` 左 | **本次 ±15°** | 250 | **1750 µs** | |
| `+15°` 右 | **本次 ±15°** | 250 | **1250 µs** | |
| `−20°` 左 | 上一版 ±20° | 333 | 1833 µs | 仅旧固件会有 |
| `+20°` 右 | 上一版 ±20° | 333 | 1167 µs | 仅旧固件会有 |
| `−30°` 左 | 初版 ±30° | 500 | 2000 µs | 电气满量程端点 |
| `+30°` 右 | 初版 ±30° | 500 | 1000 µs | 电气满量程端点 |

**要点：±15° 时不再出现 1000 / 2000 µs 端点，最大只到 1250 / 1750 µs，机械余量更足。**

### 2.3 ⚠️ 只改安卓端并不足以让全系统变成 ±15°

这是最容易踩的地方，必须说清：

| 如果只改… | 实际效果 |
| --- | --- |
| 只改安卓端 UI 为 ±15 | 安卓发出的角在 ±15 内 ⇒ **物理上确实只转 15°**（固件是「角度→脉宽」直接换算，不会放大）。✅ 能达成效果 |
| 但固件 `SAFE_*` 仍是 ±20 | 固件仍**接受** ±20 的请求 ⇒ 别的客户端可以超过 15°，安全包络没真正收窄 ⚠️ |
| 且**网页端仍硬编码发 ±20** | `protocol/Src/http_ui.c:42` 的 `SM=20`，网页的「左舵 / 右舵」按钮会继续打 ±20 ⚠️ |

**结论：要让"全系统就是 ±15°"，必须安卓端 + 固件 + 网页三处一起改。** 三处的具体改动见第 6 节。

## 4. 兼容性矩阵（四向）

| 组合 | 结论 | 具体表现 | 验证方式 |
| --- | --- | --- | --- |
| **新 APK + 新固件** | ✅ 全功能 | 双电机独立启停/换向；舵机 ±15° | 真机 TCP 联调：发 `...&m2=R`，断言 STA 回 `m2=R`；发 `servo=-15` 断言 `1750 µs` |
| **新 APK + 旧固件**（±20° 版） | ⚠️ 降级可用 | `move`/`turn`/`servo` 照常；`m2` 被旧固件当**未知字段忽略** ⇒ **M2 不动**；±15° 落在旧固件的 ±20° 内 ⇒ 被接受；STA 无 `m1`/`m2` ⇒ APK 显示"未知" | 把新 APK 连旧固件，断言：CMD 不报错、M1 能动、M2 控件无效果、状态栏两路显示未知 |
| **旧 APK + 新固件** | ⚠️ 降级可用，**但有一处硬性不兼容** | 旧 APK 发 5 字段 CMD ⇒ 被接受，`m2` 缺省=停止（**安全**，不会误动 M2）；**但旧 APK 的 ±30° 预设会被新固件回 `E_RANGE`** | 固件侧已实测：无 `m2` 的 5 字段帧被接受且 M2 落停止；`servo=-30` 被回 `E_RANGE` |
| **旧 APK + 旧固件** | ✅ 原样 | 无变化 | 回归即可 |

### 4.1 唯一需要提前知会用户的破坏性变更

**交付的 0.4.0 APK 的「左转 -30° / 右转 +30°」按钮会被新固件拒绝**（`E_RANGE`），因为舵角合法区间已从 ±30° 收窄到 **±15°**。

这不是缺陷，是需求（"减小转角"）的直接后果。三个处置选项（**建议 A**）：

- **A（推荐）**：随固件一起发布新 APK，安装说明里写明"旧 APK 的 30° 按钮在新固件上会报错，请升级 APK"。
- **B**：固件侧把"越界"从**拒绝**改成**限幅**（夹到 ±15 而不是回 `ERR`）。改动很小，但会丢掉 `E_RANGE` 这层保护。
- **C**：不处理，让旧 APK 用户在 15°~30° 区间看到错误提示。

### 4.2 为什么"旧 APK + 新固件"不会误动 M2

因为固件把 `m2` 的缺省值在**解析层显式写成停止**，而不是依赖 `memset`：

```c
/* protocol/Src/ascii_protocol.c */
memset(&command, 0, sizeof(command));
/* m2 缺省必须是 STOP。BF_MOVE_FORWARD 的枚举值就是 0，不能依赖 memset：
 * 否则老客户端不发 m2 时会被当成「M2 前进」。 */
command.m2 = BF_MOVE_STOP;
```

安卓端在新代码里也有同一个坑（`Move.FORWARD` 是枚举第一项），见 3.1。

## 6. 配套改动（**不在安卓端，但不做就会出现口径不一致**）

要做到"全系统统一 ±15°"，以下三处必须一起改：

### 6.1 固件：舵机安全行程

```c
/* app/Inc/app_config.h:111-112 */
#define CFG_SERVO_SAFE_MIN_DEG   (-15)   /* 原 -20 */
#define CFG_SERVO_SAFE_MAX_DEG   15      /* 原  20 */
```

`CFG_SERVO_FULL_SCALE_DEG` 保持 `30` **不要动** —— 动了就等于把 15° 撑满 1000–2000 µs，机械转角一点都不会变小。同时更新 L81-82、L108-110 的注释。

### 6.2 固件：宿主机测试的脉宽常量

```c
/* tests/host/Src/app_host_test.c:69-72 */
/* 左(-15 度) = 1500 + 250 = 1750us ；右(+15 度) = 1500 - 250 = 1250us ；0 度 = 1500us。 */
#define PULSE_LEFT_15DEG   1750U
#define PULSE_RIGHT_15DEG  1250U
```

`PULSE_LEFT_20DEG` / `PULSE_RIGHT_20DEG` 的引用点：L330、L412、L437、L644、L650、L750、L754、L759。断言逻辑本身不用改（它们比的都是 `CFG_SERVO_SAFE_MIN/MAX_DEG` 对应的脉宽），只需换常量与名字。

### 6.3 固件：局域网控制页的舵角幅度

```c
/* protocol/Src/http_ui.c:42 */
"<script>var m1='S',m2='S',sv=0,SM=20,tm=null,bs=0,er=0,"
                                       ↑ 改为 15
```

`SM` 就是网页「左舵 / 右舵」按钮发出的角度。不改的话，**网页仍会发 ±20°**。

> 顺带说明一处**有意保留**的行为差异：网页端 `/cmd?servo=` 与 `/servo?deg=` 走的是 `ClampServo()`，**越界会静默夹紧**；而 ASCII 协议 `servo=` 越界是**回 `E_RANGE` 整条拒绝**。同一个 `servo=-30`，网页能用、APK 报错。这是既有设计（网页是宽松的便利面），但文档里一直没写明，容易被误判成"网页限位失效"。
