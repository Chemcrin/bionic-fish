# 仿生鱼 Android—ESP—STM32 通信协议

## 1. 适用范围与版本边界

本文描述 Android 应用经 ESP-01S 与当前 STM32 固件交换的 V1 ASCII 协议。STM32 为执行与安全策略的唯一主控；Android 只发送命令并显示回传。

当前固件可识别 `CMD`，并输出 `ACK`、`ERR`、`STA`。它没有已确认的专用 `HELLO`、`PING` 或设备类型帧，因此应用不能默认发送这些扩展帧。版本/设备类型的显式协商属于待 ESP/STM32 同步实现的后续协议能力。

## 2. 帧与流式解析

```text
<TYPE,key=value,key=value,...>\n
```

- 字符编码为 UTF-8 的 ASCII 子集；帧尾为 LF，接收端可兼容 CRLF。
- TCP、UDP 和 Mock 共用同一编解码层。
- TCP 接收器必须保留半帧，连续提取粘在一起的多帧；UDP 也不能假定一次数据报必然只有一帧。
- 遇到新的 `<` 可重新同步；超长帧、非法控制字符、错误数值、缺失/重复已知字段或错误结束符必须丢弃该帧，不能提交部分命令。
- 未知且语法正确的 `key=value` 字段忽略，以便扩展；未知字段不得改变当前控制状态。
- 最大帧长度和半帧等待时间必须集中配置。Android 限制不得小于当前 STM32 的 191 字节有效载荷能力，也不得无限缓存恶意输入。

## 3. 控制帧 `CMD`

```text
<CMD,seq=12,move=F,turn=L,step_speed=60,servo=-30>\n
```

以下五个字段全部必填，顺序可变：

| 字段 | 取值 | 应用校验与含义 |
| --- | --- | --- |
| `seq` | 0~65535 | 16 位序号；每个新命令递增并允许 65535→0 回绕。 |
| `move` | `F` / `R` / `S` | 前进/反向/停止；当前固件默认拒绝 `R`。 |
| `turn` | `L` / `R` / `C` | 左/右/居中，必须与舵机角符号一致。 |
| `step_speed` | `60` / `100` | 步进电机目标档位；停止帧也必须携带一个合法档位。 |
| `servo` | -30~30 | 相对中位角（度）；应用限幅后发送，固件再次限幅。 |

组合规则：

- `turn=L` 对应负角，`turn=R` 对应正角，`turn=C` 对应 `servo=0`。
- 标准安全停止为 `move=S,turn=C,servo=0`；`step_speed` 保留最近合法档位或使用配置的 60 档，但不代表停机时仍转动。
- 默认 `move=R` 会收到 `E_STEP_REVERSE_UNSUPPORTED`。
- 步进硬件参数尚未确认时，`move=F` 会收到 `E_STEPPER_HW_UNCONFIRMED`；应用必须保留停止能力并显示该原因。
- 旧版 `n20_dir`、`n20_pwm` 即使被 STM32 当作未知字段忽略，也不得由新版 Android 发送、保存或显示。TB6612 的 B 桥已经属于步进线圈 B。

## 4. 状态帧 `STA`

```text
<STA,seq=12,link=1,step_rpm=60,step_est=60,step_actual=NA,servo=-30,roll=1.2,pitch=-2.4,yaw=85.7,err=0>\n
```

| 字段 | 类型/单位 | UI 处理 |
| --- | --- | --- |
| `seq` | 0~65535 | 与最近控制序号关联；不能单独证明命令已执行。 |
| `link` | 0/1 | 表示 STM32 最近收到有效控制帧，不等于 Wi-Fi Socket 本身在线。 |
| `step_rpm` | RPM 档位 | 当前已接受目标；停止/失联/门禁时为 0。 |
| `step_est` | RPM 估算 | 由换相节拍推算，不是真实机械反馈。 |
| `step_actual` | RPM 或 `NA` | 当前硬件固定 `NA`；UI 显示“无测速反馈”。 |
| `servo` | ° | 固件最终限幅后的命令角，不是舵面传感器反馈。 |
| `roll`,`pitch`,`yaw` | ° 或 `NA` | 姿态无效或过期时显示 `NA`/无效，不以 0 代替。 |
| `err` | 十进制位图 | 可同时包含多个活动故障，逐位解释。 |

状态视图同时显示收到时间和新鲜度。超过应用配置的状态过期阈值后，所有数值必须标“数据过期”；不得仅保留旧值却仍显示为实时。

### 4.1 `err` 位图

| 位 | 值 | 名称/含义 |
| ---: | ---: | --- |
| 0 | 1 | STM32 有效控制帧失联超时。 |
| 1 | 2 | ESP/USART2 接收溢出或字节丢失。 |
| 2 | 4 | JY61P 姿态数据超时。 |
| 3 | 8 | JY61P 软件 I²C 恢复失败。 |
| 4 | 16 | 步进线圈/参数确认门禁未解除。 |
| 5 | 32 | STM32 UART 发送队列丢弃。 |
| 6 | 64 | 保留；不得解释成已删除的 N20 故障。 |
| 7 | 128 | OLED 软件 I²C 故障。 |
| 8 | 256 | STM32 关键配置不一致。 |

未知的高位必须以“未知故障位 0x…”保留显示，不能因客户端版本较旧而吞掉。

## 5. ACK 与 ERR

```text
<ACK,seq=12,result=OK>\n
<ACK,seq=12,result=DUP>\n
<ERR,seq=12,code=E_RANGE>\n
<ERR,seq=NA,code=E_FORMAT>\n
```

- `ACK,OK`：新命令通过校验并提交。
- `ACK,DUP`：同序号、同内容的幂等重传；可以刷新保活但不得重复产生边沿动作。
- `ERR`：命令未提交。`seq=NA` 表示无法从非法帧可靠提取序号。

应用至少识别并给出可操作说明：`E_FORMAT`、`E_FRAME_TIMEOUT`、`E_TOO_LONG`、`E_TYPE`、`E_FIELD`、`E_DUP_FIELD`、`E_MISSING_FIELD`、`E_RANGE`、`E_SEMANTIC`、`E_SEQ_CONFLICT`、`E_SEQ_OLD`、`E_SEQ_AMBIGUOUS`、`E_STEP_REVERSE_UNSUPPORTED`、`E_STEPPER_HW_UNCONFIRMED`、`E_CONFIGURATION`、`E_RX_OVERFLOW`。未知错误码原样保留到调试视图和日志。

## 6. V1 握手与保活

### 6.1 兼容握手

连接建立后，应用先发送五字段安全停止帧：

```text
<CMD,seq=N,move=S,turn=C,step_speed=60,servo=0>\n
```

只有以下条件成立时，才把设备标记为“协议可用”：

1. 在握手超时内收到相同 `seq` 的 `ACK,result=OK` 或 `DUP`；
2. 在同一握手窗口内解析到该 `seq`、`link=1` 且字段合法的 `STA`。两帧到达先后不作假设。

这能验证当前 V1 行为，但不能可靠证明设备型号，也不是身份认证。若产品必须核验 `protocol_version` 和 `device_type`，需要先为 ESP/STM32 定义并实现新帧，再通过能力协商启用；不得仅修改 APK 就宣称已实现端到端验证。

### 6.2 心跳

当前周期 CMD 兼作 STM32 的控制保活。应用按集中配置的发送周期发送当前完整控制状态；没有运动意图时发送安全停止状态。不能默认发送固件不认识的 `PING`。

当前 STM32 V1 的 `CFG_LINK_TIMEOUT_MS` 为 1000 ms。APK 将控制帧和停止保活周期限制在 50~750 ms，为调度与网络抖动保留至少 250 ms 名义余量；默认控制/心跳周期为 200/500 ms。显式命令 ACK 超时默认 800 ms，可配置范围 100~900 ms且必须小于 APK 链路失联超时。上述值是当前固件兼容边界，并非未经实测的生产结论；ESP 队列能力、最终周期、状态过期阈值、握手超时和重连退避仍须联调。

## 7. 序号、发送队列与延迟

- 应用只为真正进入发送队列的命令分配序号；断开重连后使用新会话窗口。
- 任一时刻保持一个明确的当前控制状态。停止命令具有最高优先级，应清除尚未发送的运动状态，避免连接恢复后补发旧动作。
- 需要重发时必须复用相同序号和完全相同的五字段内容；改变内容必须使用新序号。
- 显式控制、安全停止和握手在写出前登记同序号等待器；`ACK,OK`/`ACK,DUP` 完成请求，同序号 `ERR` 令请求失败。ACK 超时会清理等待器并触发失联/重连策略。
- 周期保活复用当前已由 ACK 接受的完整命令和同一序号，不阻塞发送 actor 等待 ACK；固件以 `ACK,DUP` 幂等确认。未经 ACK 接受或收到 ERR 的新运动命令不会成为周期目标。
- 未知/过期序号只记录，不倒退 UI 状态；未知帧类型也不会刷新 APK 的受支持协议看门狗。
- 协议延迟可按“发送 CMD 到收到同序号 ACK”的单调时钟差估计。它是应用层往返时间，不是单向网络延迟。
- 日志需要记录方向、时间、传输、序号和结果；敏感网络信息导出前应让用户知情。

## 8. 连接超时与安全状态机

```text
未连接 → 扫描中 → 连接中 → V1握手 → 已连接
                                  ↓失败
                         失联/错误 → 重连中
已连接 → 安全断开中（禁用普通控制）→ 未连接
```

- 用户可随时取消扫描；连接/重连阶段可执行安全断开。活动会话期间拒绝扫描，避免扫描过程使周期保活中断。
- Socket 关闭、读写错误、握手失败、显式请求 ACK 超时或所有受支持入站帧持续静默时，UI 显示具体原因并进入相应失败/失联/重连策略。只有 `STA` 过期但仍持续收到合法 ACK/ERR 时，遥测标为“数据过期”，不会伪称实时，也不会仅凭该条件销毁 Socket。
- 断开、控制页退出、应用进入后台时，应用尽力发送一帧高优先级安全停止并等待 ACK；失败会提示/记录。停止意图一建立就截断旧运动队列并同步清除 UI 的旧运动状态，即使网络发送失败也不会在恢复前台后复活旧 `move=F`。
- 切换设备前必须先对旧设备执行同样的安全停止；`DISCONNECTING` 阶段禁止插入普通命令。连接意图/会话代次会丢弃旧链路迟到事件及过期重连任务。
- 网络安全停止不是可靠急停：进程被系统杀死、Wi-Fi 已断或 ESP 掉电时无法发送。STM32 自身失联逻辑应在约 1000 ms 停止步进并按配置使舵机回中，硬件仍需独立失效保护。
- 重连成功后必须重新安全握手，不能自动恢复断线前的运动命令。

## 9. 传输配置

TCP/UDP 仅承载上述字节流/帧，不改变字段。以下配置必须集中保存并在 UI 标为“待确认”或由用户输入：

- 传输类型、ESP 工作模式、主机/IP、控制端口、发现端口；
- 发现协议、服务名或广播探测载荷；
- 连接/读写/握手/ACK/状态过期超时及重连退避；
- 将来真实蓝牙硬件的 Classic UUID 或 BLE service/characteristic UUID。

未确认参数不得用看似真实的硬编码地址或 UUID 填充。Mock 参数不能被误存为真实设备配置。
