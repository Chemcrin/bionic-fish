# ② 通信调试

**目标**：让 STM32 ↔ ESP-01S ↔ 手机 这条链路真正跑通，并且**每一步都可观测**。

**完成标志**：手机连上 `BionicFish-AP` 后能完成 STOP/ACK/STA 握手，App 显示「已连接」；串口能看到 `server=1`、`tcp=1`。

---

## 一、链路全貌

```text
┌──────────────┐
│ Android 控制台 │
└──────┬───────┘
       │ Wi-Fi：BionicFish-AP（192.168.4.1）
       │ TCP：端口 9000
┌──────▼───────┐
│  ESP-01S      │  AT 固件 ｜ 纯 SoftAP ｜ TCP Server
└──────┬───────┘
       │ UART0 ↔ USART2，115200-8N1，无流控，交叉收发
┌──────▼───────┐
│ STM32F103C8T6 │
└──────┬───────┘
       │ USART3 → CH340 → Type-C（只发不收，日志与状态帧）
┌──────▼───────┐
│  电脑串口助手  │
└──────────────┘
```

| 参数 | 值 |
| --- | --- |
| SSID / 密码 | `BionicFish-AP` / `12345678` |
| AP / 网关 | `192.168.4.1` |
| 掩码 | `255.255.255.0` |
| 传输 | TCP Server，端口 `9000` |
| Wi-Fi 模式 | `AT+CWMODE=2`（**纯 SoftAP**） |
| 串口 | 115200 / 8N1 / 无流控 |

## 二、双通道调试：先把「眼睛」装上

在调通信之前，**必须先能看见设备在说什么**。这就是拓展板把 SWD 与板载 CH340 做成两条独立通道的价值。

| 通道 | 物理接口 | 用途 |
| --- | --- | --- |
| SWD | ST-Link（`PA13`/`PA14`） | 烧录、断点、halt 查寄存器 |
| 串口 | 板载 CH340 + Type-C（`USART3`） | 运行期日志与状态帧，**只发不收** |

**两条通道物理独立、互不抢占，可以同时接在同一台电脑上。**

### 2.1 接入步骤

1. Type-C 线接电脑，在设备管理器中确认多出一个 COM 口（CH340）。
2. 用串口助手打开该端口：**115200 / 8-N-1 / 无流控**。
3. 上电，应看到周期性输出。

### 2.2 应该看到什么

```text
ESP server=1 tcp=0 reset=0 error=OK
```

| 字段 | 含义 |
| --- | --- |
| `server=1` | TCP 服务初始化完成 |
| `tcp=1` | 已有控制客户端连上 |
| `reset=0` | 不需要复位 ESP（`reset=1` 表示需实际复位） |
| `error=OK` | 无错误 |

**这是判断链路状态的第一手信息**，比看手机界面可靠得多。

## 三、ESP-01S 配置

### 3.1 固件版本要求

| 项 | 要求 |
| --- | --- |
| AT 版本 | **AT 1.7.4.0**（实物已验证） |
| SDK | SDK 3.0.5-dev (52383f9)，编译于 2020-08-28 |
| 串口参数 | `115273,8,1,0,0` —— 对应约 115200、8N1、无流控 |

确认方法：用 AT 指令查版本，回包应包含上述版本号。**匹配 NONOS 分支**，保留现有固件即可，无需重刷。

> ⚠️ 若你的 ESP-01S 固件版本不同，AT 命令集可能有差异（NONOS AT 1.7.4/1.7.5 与 ESP-AT 2.x 不同）。请核对实际 `AT+GMR` 结果后再继续。

### 3.2 关键配置：Wi-Fi 模式必须是 2

```text
AT+CWMODE=2      ← 纯 SoftAP，必须是 2
```

> 🔴 **绝不能用 `AT+CWMODE=3`（AP+STA 双模）。**
>
> 本项目曾出现过这个回归，后果是**网页完全打不开**：固件从不下发 `AT+CWJAP`，STA 侧永远拿不到凭据，ESP 反复去连 flash 里残留的旧 AP；双模下还要同时维护 DHCP 与多个 socket 槽位，最终**客户端拿不到 IP**。
>
> 若将来确实需要启用双模，**必须同时实现 `AT+CWJAP` 下发**。

### 3.3 其他必要配置

| 指令 | 作用 |
| --- | --- |
| `AT+CIPMUX=1` | 多连接模式（AT 事务需要） |
| `AT+CIPSERVER=1,9000` | 启动 TCP 服务，端口 9000 |
| `AT+CIPSTO=3` | TCP 空闲 3 秒自动断开（**注意：这是已知问题的来源**，见下方） |

**固件的 AT 事务纪律**（复刻时不要绕过）：

- 逐命令下发并**等待自身响应**，不用 `ATE0` 的 OK 代替 `CIPSERVER` 成功。
- 发送先等 `CIPSEND` 的 `>` 提示，再发**声明的准确字节数**，最后等 `SEND OK`。
- 不能确认 ESP 是否仍在等待数据时，**不要把 `AT+RST` 或 `+++` 盲发成载荷**。

> ⚠️ **已知问题：`CIPSTO=3` 会导致 App 连上就断。**
>
> ESP 空闲 3 秒即断开，而 App 在无命令时只 delay、不发帧，于是连接反复重建。可选修复方向：放宽 `CIPSTO`（如 30 s），或让 App 周期发心跳。**本项目未修复此项**，属已知待改进点。

## 四、协议联调

协议采用**可打印 ASCII + 换行分帧**，就是为了让复刻者能用任意串口工具直接调试，不必写解码器。

### 4.1 帧格式

```text
<TYPE,key=value,key=value,...>\n
```

- 帧尾必须 `LF`，接收端也接受 `CRLF`。
- 字段值不得含 `<`、`>`、`,`、`=`、换行或 NUL。
- 最大载荷 191 字节（`CFG_PROTOCOL_PAYLOAD_MAX-1`）。
- 组帧超时 250 ms；超时、超长、不可打印字符均丢弃并重新同步。

### 4.2 控制帧（Android → ESP → STM32）

```text
<CMD,seq=12,move=F,turn=R,step_speed=60,servo=-15,m2=R>\n
```

五个基础字段必填，`m2` 选填：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `seq` | `0`~`65535` | 16 位序号，用于重复/乱序检测 |
| `move` | `F`/`R`/`S` | **M1（370 推进）** 前进 / 反向 / 停止 |
| `turn` | `L`/`R`/`C` | 左 / 右 / 居中，**必须与 `servo` 符号一致** |
| `step_speed` | `60`/`100` | 占空比挡位：`100`=满速挡（95%）、`60`=低速挡（60%）。**只接受这两个值** |
| `servo` | `-15`~`15` | 相对中位角（度），超范围直接返回 `E_RANGE` |
| `m2` | `F`/`R`/`S` | **选填**，**M2（N20 唧筒）** 推 / 拉 / 停。**缺省 = 停止** |

**两条容易出错的地方**：

1. **`turn` 与 `servo` 的符号必须一致。** `turn=L` 必须配负 `servo`，`turn=R` 配正，`turn=C` 配 `servo=0`；不一致返回 `E_SEMANTIC`，不会静默替你选一个。
2. **`m2` 缺省是「停止」，不是「保持原状态」。** 不写 `m2` 字段，唧筒就会停。

> 📌 `step_speed` 是**历史字段名**（旧步进方案用它选转速档）。字段名与「必填」约束保留以兼容旧客户端，但它现在承载的是**直流电机占空比挡位**，不是步进速度。

### 4.3 状态帧（STM32 → ESP / CH340）

```text
<STA,seq=12,link=1,step_rpm=NA,step_est=NA,step_actual=NA,step_on=1,servo=-15,roll=1.2,pitch=-2.4,yaw=85.7,m1=F,m2=R,err=0>\n
```

周期 200 ms 发送。

| 字段 | 含义 |
| --- | --- |
| `link` | 最近收到有效命令则为 1。**只表示应用控制链路新鲜，不证明 Wi-Fi 或手机真的在线** |
| `step_rpm` / `step_est` / `step_actual` | 固定 `NA`（无编码器，不做转速估算） |
| `step_on` | M1 是否处于运行；**不证明机械轴实际转动** |
| `servo` | 限幅后的**命令角**，不等于实际舵面反馈 |
| `roll` / `pitch` / `yaw` | 有效时输出姿态角；读不到为 `NA`，**不能把 0.0 当有效测量** |
| `m1` / `m2` | 当前已下达的方向 |
| `err` | 当前活动故障位图的十进制值 |

### 4.4 握手流程

```text
1. 手机加入 BionicFish-AP（保持该 Wi-Fi，即使提示无互联网）
2. App 发送完整合法的 STOP CMD
3. 收到同序号 <ACK,seq=N,result=OK>
4. 收到 link=1 的 STA
   → 此时才显示「已连接」
```

> ⚠️ **加入 Wi-Fi 或连上 TCP 本身都不等于握手完成。** 必须走完 STOP → ACK → STA 三步。

### 4.5 手动调试示例

用串口工具直接发（注意行尾 `\n`）：

```text
发送：<CMD,seq=1,move=S,turn=C,step_speed=60,servo=0>
预期：<ACK,seq=1,result=OK>

发送：<CMD,seq=2,move=F,turn=R,step_speed=60,servo=-15,m2=R>
预期：<ACK,seq=2,result=OK>

发送：<CMD,seq=3,move=F,turn=R,step_speed=60,servo=15>
预期：<ERR,seq=3,code=E_SEMANTIC>     ← turn=R 配了负 servo
```

## 五、故障定位

### 5.1 定位思路

**分层判断，不要一次怀疑所有环节。**

```text
串口有输出吗？
  ├─ 没有 → MCU 层面问题（供电/时钟/烧录）→ 回 [硬件制造.md](硬件制造.md)
  └─ 有 → 看 server= 字段
            ├─ server=0 → ESP 初始化失败 → 查 AT 固件版本、UART 交叉、3.3V 供电
            └─ server=1 → 看 tcp= 字段
                           ├─ tcp=0 → 手机没连上 → 查 Wi-Fi、IP、端口
                           └─ tcp=1 → 查握手 → 查 seq、字段合法性、turn/servo 一致性
```

### 5.2 常见现象

| 现象 | 排查方向 |
| --- | --- |
| **AP 能加入，但网页/TCP 打不开** | **查 `CFG_ESP_WIFI_MODE` 是否为 2**（纯 AP）；查 `server=` 是否为 1 |
| 串口完全没有输出 | 供电、时钟配置、烧录是否成功 |
| `server=0` | ESP AT 固件版本不符、`PA2/PA3` 未交叉、ESP 供电不足（**ESP 峰值电流可达数百 mA**） |
| 姿态显示 `R:--- P:--- Y:---` | 看 USART3 的 `I2CBUS` → `IMUSCAN` → `IMU scl= sda= st= probe=` 三段诊断 |
| | `probe=` 无响应 → 多为 **`PB6/PB7` 缺 4.7 kΩ 外部上拉** |
| App 连上就断、反复重连 | **`AT+CIPSTO=3` + 固件只接受单个控制客户端**；**已知未修复项** |
| 收到 `E_RX_OVERFLOW` | UART 环形缓冲溢出，固件已丢弃残帧并停机；**必须收到一帧完整合法 CMD 才能重新建链** |
| 收到 `E_SEQ_OLD` / `E_SEQ_AMBIGUOUS` | 序号回绕问题；失联或溢出后序号窗口会清除，用新序号重发 |
| 电机无响应但 ACK 正常 | 查 `CFG_MOTOR_A_ENABLED` / `CFG_MOTOR_B_ENABLED` 是否为 1；查 `err` 位图 |

### 5.3 故障位图解读

`STA.err` 是**活动故障位图**的十进制值，可多故障叠加：

| 位 | 值 | 含义 |
| ---: | ---: | --- |
| 0 | 1 | 链路超时强制断链 |
| 1 | 2 | ESP/USART2 接收缓冲溢出或 ORE |
| 2 | 4 | IMU 数据过期 |
| 3 | 8 | IMU 软件 I²C 恢复失败 |
| 4 | 16 | 该路电机被配置禁用 |
| 5 | 32 | UART 发送队列丢弃 |
| 7 | 128 | OLED 软件 I²C 异常 |
| 8 | 256 | 关键配置与定时器初始化不一致 |

**例**：`err=5` 表示链路超时（1）+ IMU 数据超时（4）**同时存在**。

> 📌 协议错误用即时 `ERR` 帧告知；`STA.err` 只描述**持续活动的运行期故障**，两者不可混用。

## 六、安全策略（必读）

### 6.1 失联保护

超过 **1000 ms** 未收到有效命令时：

1. **两路电机停止**，A/B 两桥均进入 coast，不保持未知电流；
2. 舵机回中位（由 `CFG_SERVO_CENTER_ON_LINK_TIMEOUT` 控制，默认回中）；
3. `link=0`，置链路超时故障位，主动关闭旧 TCP 连接释放槽位。

> ⚠️ **失联停机不可关闭。** 本交付不提供关闭该项的开关。

### 6.2 溢出的处理更严格

ESP 接收缓冲溢出或 UART ORE 时：**立即丢弃残帧、重置解析器、清除会话与序号窗口、停止两路电机、舵机回中**，不等待普通的 1 秒保活超时。

之后必须收到一帧**完整且通过全部校验**的 `CMD` 才能重新建链。

### 6.3 一个重要设计原则

> **任何解析、语义或序号失败，都不能造成部分电机或舵机动作。**

协议栈在校验全部通过前不触碰执行器。复刻或改造时请保持这个原则 —— 宁可不动，不可动一半。
