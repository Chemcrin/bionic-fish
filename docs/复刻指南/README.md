## 阅读前提

> ⚠️ **复刻前请先了解本项目的验证状态。** 软件层（固件主机回归、Android 单元/仪器测试）已通过，**整机也已在泳池 / 静水环境完成实际下水运行**（密封、配重、姿态与基本机动已验证）。但下列项目**尚未做过逐项定量标定**，仍需你自己在实物上确认：2 s 慢周期 + 95% 占空比下 370 电机能否稳定带载、堵转电流与 TB6612 温升、N20 唧筒的行程限位接线与动密封的长期可靠性。

**建议的复刻顺序**：

```text
① 硬件制造  ──►  ② 通信调试  ──►  ③ 电控编写
   先让硬件能通电         再让链路能通信        最后按需改固件
   （不必等全部做完）      （串口能看到日志）    （不要一上来就改代码）
```

**关键原则：不要跳步。** 这个项目里最耗时的部分不是写代码，而是**在硬件没通、链路没通的情况下改代码**。先把每一层单独验证过，再往上叠加。

## 关于 AI 助理工具：建议怎么用

本项目的开发全程有 AI Agent 参与，也**建议你在复刻时同样把 AI 助理工具纳入工作流** —— 但要用对地方：

| 适合交给工具 | 必须自己来 |
| --- | --- |
| 查数据手册、核对引脚与外设时钟配置 | 电源极性与接线顺序的最终确认 |
| 生成样板代码、改配置常量、搭测试脚手架 | 保险丝规格、限流点等安全参数取舍 |
| 解析串口日志、从 `STA` 与故障位图反推故障层 | 电机带载能力、堵转发热等实机行为判读 |
| 把报错、寄存器值与现象串起来做假设推演 | 防水、配重、下水前的安全检查 |

**为什么这个项目能这么用**：因为硬件上预留了**双通道闭环**（见 [3.5.2 节](../../README.md#352-板载-ch340-的实战价值双接-ai-agent-联合调试)）—— SWD 能烧录、CH340 能读日志，工具才有「改 → 烧 → 看 → 再改」的抓手。**没有可观测性，AI 只能猜；有了可观测性，AI 才能定位。**

> ⚠️ **底线**：工具给出的任何电气结论，都要用万用表／示波器在你的实物上复核后才能采信。AI 的强项是提效，不是替你承担实机风险。

## 三条最容易踩的坑（先看这个）

在动手前，请务必知道这三件事 —— 它们都不是数据手册里显著位置的提示，但直接决定复刻能否成功：

### 1. 满速挡必须是 95%，不能是 100%

100% 占空比在 STM32F1 上落成 `CCR = ARR + 1`，PWM 输出**恒为高电平、永不产生下降沿**。TB6612 的 PWM 输入依赖持续开关边沿维持高侧栅极/自举驱动，恒定高电平会让**自举电容无法刷新**，结果是「有 12 V、STBY 已拉高，电机却带不动负载」。

详见 [README 3.4 节](../../README.md#34-一个典型的硬件陷阱为什么满速挡是-95-而不是-100)。

### 2. Wi-Fi 模式必须是 2（纯 AP），不能是 3

`AT+CWMODE=3`（AP+STA 双模）会导致**网页完全打不开**：固件从不下发 `AT+CWJAP`，STA 侧永远拿不到凭据，ESP 反复去连 flash 里的旧 AP，双模下还要同时维护 DHCP 与多个 socket 槽位，最终客户端拿不到 IP。

详见 [README 5.1 节](../../README.md#51-通信链路)。

### 3. 保险丝不防接反

XT60 极性接反会**直接击穿稳压模块与所有模组**。上电前必须用万用表确认极性。

## 方向间的依赖关系

```text
┌─────────────────┐
│  ① 硬件制造      │  产出：一台能通电、能上电的裸机
│  采购 · 接线 · 打印 │
└────────┬────────┘
         │ 双通道（SWD + CH340）就位
         ▼
┌─────────────────┐
│  ② 通信调试      │  产出：串口能看到 STA，手机能握手
│  ESP 配置 · 协议  │
└────────┬────────┘
         │ 链路已验证
         ▼
┌─────────────────┐
│  ③ 电控编写      │  产出：按自己需求改造的固件
│  构建 · 结构 · 扩展│
└─────────────────┘
```

**为什么按这个顺序**：② 的每一步都需要 ① 提供可观测的硬件（串口、SWD）；③ 的每次改动都需要 ② 提供可读的日志反馈。反过来做，你会同时面对「代码可能错、硬件可能错、链路可能错」三重不确定，无法定位。
