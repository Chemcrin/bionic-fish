# ③ 电控编写

**目标**：能构建固件、看懂代码结构、按自己的需求改参数或扩展功能。

**完成标志**：能独立完成「改一个参数 → 构建 → 烧录 → 用串口验证」的完整循环。

---

## 一、构建环境

### 1.1 固定依赖

| 组件 | 版本 |
| --- | --- |
| STM32CubeF1 | **v1.8.6**（与 `bionic_fish.ioc` 一致），commit `42472d60…` |
| Arm GNU Toolchain | **13.3.Rel1**，目标 `arm-none-eabi` |
| CMake | 3.31.8（工程最低 3.20） |
| Ninja | 1.12.1 |
| Python | 3.9+（仅构建包装脚本需要） |
| 主机测试编译器 | GCC / Clang（**必须与 Arm 工具链分开**） |

> ⚠️ **版本不能随意替换。** CMake 会拒绝非 v1.8.6 的 CubeF1 `package.xml`。下载地址与校验值固定在 `dependencies.lock.json`。

### 1.2 首次构建（Windows）

在 `STM32控制工程` 目录：

```powershell
python scripts/build.py firmware --bootstrap
python scripts/build.py host --bootstrap --host-cc C:/path/to/native-gcc.exe
```

- `--bootstrap` 会自动下载校验后的工具与固定版本 CubeF1，默认缓存到 `%LOCALAPPDATA%/bionic-fish-build`；**第二次不需要再加这个参数**。
- 所有 PATH 设置**只传给本次子进程**，不修改你的全局环境，也不自动烧录。

> ⚠️ **宿主测试不要指定 `arm-none-eabi-gcc`** —— 它生成不了能在电脑上跑的程序。若本机 `gcc` 已配好，`--host-cc` 可省略。

### 1.3 Linux / macOS

```sh
python3 scripts/build.py firmware --bootstrap --toolchain-bin /opt/arm-gnu-toolchain/bin
python3 scripts/build.py host --host-cc /usr/bin/gcc
```

或不用 Python，直接走 CMake：

```sh
cmake -S . -B build-firmware -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi-gcc.cmake \
  -DARM_TOOLCHAIN_BIN=/path/to/arm/bin \
  -DSTM32CUBE_F1_PATH=/path/to/STM32Cube_FW_F1_V1.8.6 \
  -DBIONIC_FISH_BUILD_FIRMWARE=ON -DBIONIC_FISH_BUILD_HOST_TESTS=OFF \
  -DCMAKE_BUILD_TYPE=MinSizeRel -DBIONIC_FISH_WERROR=ON
cmake --build build-firmware --parallel
```

> 📌 换编译器或生成器时**必须换新的 `--build-dir`**，不要复用另一工具链的 CMake 缓存。

### 1.4 产物

输出在 `build-firmware/`：`bionic_fish.elf`、`bionic_fish.bin`、`bionic_fish.map`，另生成 `build-info.json`（记录编译器、CubeF1、源提交、是否有未提交修改、产物 SHA-256）。

**参考基线**：BIN 约 **34,272 字节**，Flash 占用 **52.29%**、RAM **79.92%**。

> ⚠️ **RAM 已用近 80%，加功能前先算内存账。** 链接脚本限定 64 KiB Flash / 20 KiB SRAM，预留 0x200 堆与 0x800 栈，超区会直接链接失败。

## 二、代码结构

固件约 **6,000 行 C**，严格分层。`main.c` 只做初始化与主循环调度，业务逻辑不堆在入口文件。

```text
STM32控制工程/
├── Core/          CubeMX 生成层（时钟、GPIO、TIM、USART）
├── app/           应用层
│   ├── app.c          主循环调度、命令分发、超时检查
│   └── app_config.h   ★ 全部可调参数的唯一入口
├── bsp/           板级支持层
│   ├── bsp_board.c    板级初始化、紧急 coast
│   ├── bsp_time.c     32 位微秒时基（TIM4 扩展）
│   ├── bsp_uart.c     环形缓冲收发、错误回调
│   └── esp_link.c     ★ ESP-01S AT 状态机
├── protocol/      协议层
│   ├── ascii_protocol.c  V1 ASCII 组帧/解析/校验
│   ├── http_ui.c         内嵌网页控制页
│   └── ring_buffer.c     无锁环形缓冲
├── cmake/         工具链与链接脚本
├── scripts/       构建、烧录、串口工具
└── tests/         主机回归测试
```

> 📌 完整的控制层（`motor_control.c` / `servo_control.c`）、驱动层（`soft_i2c.c` / `ssd1306.c` / `jy61p.c`）、界面层（`oled_ui.c`）分文件同属上述体系，职责边界按目录划分。

### 2.1 五条设计原则（改代码时请遵守）

**① 中断只做搬运，主循环做决策**
UART 中断仅把字节写入固定大小环形缓冲，完整帧解析在主循环完成。中断里不做阻塞业务，也不直接驱动执行器。

**② 固定内存，无动态分配**
所有缓冲、字段表、状态槽均为固定大小数组，业务代码**不使用 `malloc`**。这保证 RAM 占用可预测，也避免长期运行的碎片化风险。

**③ 配置集中于单一入口**
所有可调参数集中在 `app_config.h`，并配编译期静态校验。定时器折算、占空比边界、舵机行程一致性全部在**构建期**拦截。

**④ 用编译期门禁防止回归**
曾因缓冲不匹配导致「网页静默发不出去」：响应缓冲 4096 字节，传输缓冲只有 3584，**超长一个字节都发不出去，而串口上 `error=OK`，整个失败过程完全静默**。

修复后加了门禁：

```c
/* esp_link.c —— 今后只要有人再让传输缓冲小于响应缓冲，构建直接失败 */
static char kHttpRawMustFitResponse[
    (HTTP_RAW_BYTES >= HTTP_RESPONSE_BYTES) ? 1 : -1];
```

**⑤ 执行器动作原子化**
任何解析、语义或序号失败，都**不能造成部分电机或舵机动作**。协议栈在校验全部通过前不触碰执行器。

## 三、配置方法

### 3.1 改参数

**所有可调项都在 `app/Inc/app_config.h`**，不要在业务代码里写魔数。

| 想改什么 | 配置项 | 当前值 |
| --- | --- | --- |
| 满速挡占空比 | `CFG_MOTOR_FULL_DUTY_PERCENT` | `95U`（**不要改成 100**） |
| 低速挡占空比 | `CFG_MOTOR_LOW_DUTY_PERCENT` | `60U` |
| 单独禁用 M1 | `CFG_MOTOR_A_ENABLED` | `1U` |
| 单独禁用 M2 | `CFG_MOTOR_B_ENABLED` | `1U` |
| 失联超时 | `CFG_LINK_TIMEOUT_MS` | `1000UL` |
| 状态帧周期 | `CFG_STATUS_PERIOD_MS` | `200UL` |
| 舵机安全行程 | `CFG_SERVO_SAFE_MIN/MAX_DEG` | `-15` / `15` |
| 失联是否回中 | `CFG_SERVO_CENTER_ON_LINK_TIMEOUT` | `1U` |
| Wi-Fi 模式 | `CFG_ESP_WIFI_MODE` | `2U`（**必须是 2**） |
| AP 名称/密码 | `CFG_ESP_AP_SSID/PASSWORD` | `BionicFish-AP` / `12345678` |
| 端口 | `CFG_ESP_TCP_PORT` | `9000U` |
| 调试按键 | `CFG_DEBUG_BUTTONS_ENABLED` | `1U`（**下水前必须改 0**） |
| 两挡 PWM 定时器 | `CFG_MOTOR_TIM_PRESCALER/PERIOD` | `7199U` / `19999U`（→ 2 s 周期） |

### 3.2 两处「改了就坏」的配置

**① `CFG_MOTOR_FULL_DUTY_PERCENT` 不要改成 100。**

100% 会让 `CCR = ARR + 1`，PWM 恒高、**永不产生下降沿**，TB6612 自举电容无法刷新，结果就是「有电压却带不动负载」。**95% 是功能必需，不是保守取值。**

**② `CFG_ESP_WIFI_MODE` 不要改成 3。**

双模会导致网页完全打不开（原因见 [通信调试.md](通信调试.md)）。要启用 3，**必须同时实现 `AT+CWJAP` 下发**。

### 3.3 下水的强制动作

```c
#define CFG_DEBUG_BUTTONS_ENABLED   0U   /* 1U → 0U */
```

> 🔴 **这一项是安全项，不是功能项。** 调试按键功能有意放开了「无链路即无运动」的看门狗保证 —— K1 启动的转动在**完全没有上位机时会一直持续**。

## 四、验证方法

### 4.1 三层验证

```text
① 主机回归测试   → 逻辑对不对（在 PC 上跑，秒级）
② Arm 交叉构建   → 能不能编进芯片（编译期门禁在这一层拦截）
③ 目标板实测     → 实物行为对不对（唯一能证明硬件的）
```

**前两层通过不代表第三层通过。** 顺序执行，不要跳。

### 4.2 主机测试

```sh
python scripts/build.py host --host-cc /usr/bin/gcc
```

基线：**16/16 通过**（含编译期门禁）。

> 📌 Release / MinSizeRel 构建**也保留断言**，不要为了性能关掉。

### 4.3 目标板验收

见 [验收检查清单.md](../../仿生鱼完整项目交付包_v1/仿生鱼完整项目交付包/STM32控制工程/验收检查清单.md)。核心判据：

- 两路电机可同时下达方向（`move=` 与 `m2=`），互不覆盖；
- STOP / 失联 / UART 丢失使**两路同时 coast**；
- 舵机 ±15° 限幅，±16° 返回 `E_RANGE`；
- 网页左键确实左转、右键确实右转（方向不双重取反）。

## 五、扩展实践

### 5.1 扩展一：把唧筒限位开关接进固件

**当前状态**：机械件的限位开关**已设计但未接线**，活塞行程保护需自行补充。这是最值得做的第一个扩展。

思路：

1. 选两个空闲 GPIO 作限位输入（配置为输入 + 内部上拉，低有效）。
2. 在 `app_config.h` 增加限位引脚与消抖时间配置。
3. 在主循环中轮询限位状态；**触发时立即令 M2 coast**，并置一个故障位。
4. 在 `m2` 命令的下发路径上加前置判断：若已触发同向限位，直接拒绝并回 `ERR`。

> ⚠️ 注意原则 ⑤：限位触发必须**只停 M2，不影响 M1 与舵机**。不要写成全局急停。

### 5.2 扩展二：修复 App 连上就断

**当前状态**：`AT+CIPSTO=3` 使 ESP 3 秒空闲即断开，而 App 在无命令时只 delay、不发帧，导致反复重建连接。**已知未修复。**

两个方向，任选其一：

| 方向 | 做法 | 取舍 |
| --- | --- | --- |
| 放宽 `CIPSTO` | 改为 30 s | 改动最小，但断链检测变慢 |
| App 发心跳 | 加一个低频 keepalive 命令 | 更健壮，但需同时改协议与 App |

> 📌 若选心跳方案，建议新增独立的帧类型（如 `KEEP`）而非复用 `CMD`，避免污染控制语义与序号窗口。

### 5.3 扩展三：支持多控制客户端

**当前状态**：固件只接受**单个**控制客户端，安卓与网页无法同时连接。

`CFG_ESP_MAX_CLIENTS` 当前为 `4`，但**协议层只维护一个会话槽位**。要真正支持多客户端，需要在会话层维护多组「序号窗口 + 保活计时」，并决定：

- 多客户端命令冲突时谁优先？（建议后到者覆盖，或直接拒绝）
- 断线时是否只清对应那个会话的窗口？

> ⚠️ 这是**结构性改动**，不是改个宏的事。改之前先把序号窗口与会话生命周期的关系想清楚。

### 5.4 扩展四：加一个传感器（以 MS5837 水深为例）

1. **接总线**：两条软件 I²C 已各自占用，建议复用 IMU 那条（`PB6/PB7`，注意地址不冲突）。
2. **加驱动**：仿照 `jy61p.c` 写一个固定内存、带失败计数的读函数。
3. **加状态字段**：在 `STA` 中新增字段。**新增字段是向后兼容的**（未知字段会被忽略），但请确认 App 侧不会因此解析失败。
4. **加故障位**：在 `faults.h` 中占用 bit 6（当前预留）—— ⚠️ **bit 7/8 的位置不得前移**，否则会破坏既有位图语义。

### 5.5 扩展的通用检查清单

- [ ] 新参数是否加进了 `app_config.h` 并配了编译期校验？
- [ ] 是否引入了动态分配？（不允许）
- [ ] 中断里是否做了决策？（不允许）
- [ ] 失败路径是否可能造成**部分执行器动作**？（不允许）
- [ ] RAM 增量是否算过？（余量只剩约 20%）
- [ ] 是否跑了主机回归测试？
- [ ] 是否在实板上验证过？

## 六、CubeMX 再生成政策（重要）

> 🔴 **禁止在交付源码目录直接点 Generate Code，并把结果当作可烧录版本。**

CubeMX 的 `KeepUserCode` **只保护 USER CODE 区**，无法保留自定义的完整时钟映射、MSP、安全 GPIO 初始化、HAL 配置和构建源列表。

正确流程：

1. 把 `bionic_fish.ioc` 复制到**仓库之外的临时目录**，用 CubeF1 **v1.8.6** 生成。
2. 对比生成文件与受维护 `Core/` 的差异，**只合并本次需要的引脚/外设变更**；同步更新 `.ioc` 与 `app_config.h`。
3. 保留 `main.c` 中已标记的 Includes、PD、2、3、4 与 `Error_Handler_Debug` 区域。**必须存在** `BSP_Time_Init`、`App_Init`、循环中的 `App_Process`，以及 TIM4、UART RX/TX/Error 回调向 BSP 的转发。
4. 特别复查：**两桥启动 coast**、舵机初始脉宽、TIM4 更新中断、USART2/3、SWD、两条软件 I²C 的开漏配置。保留标准 `assert_param` 定义与 `Core/Src/assert.c`。
5. 完整执行主机测试 + 固件交叉构建，再上板空载验收。

## 七、调试技巧

### 7.1 利用双通道

```text
改代码 ──► SWD 烧录 ──► 串口读 STA/诊断 ──► 定位 ──► 再改
```

**串口是主要的信息来源。** 全链路诊断都通过 USART3 以纯文本输出，包括：

- `ESP server=… tcp=… reset=… error=…` —— 链路状态
- `IMU scl= sda= st= probe=` —— IMU 三段诊断
- `STA` 状态帧 —— 完整运行状态与故障位图

### 7.2 已知的烧录坑

烧录报 `failed to erase memory` / `failed to download Sector[0]` 时：

**先用「写 RAM `0x20000000`」做对照实验** —— RAM 成功而 flash 失败，即可判定为 **MCU 内部 flash 故障**，与代码无关，需换芯片。

> ⚠️ `-e all` 报「Mass erase successfully achieved」**不表示擦除真的生效**。

### 7.3 构建诊断的正常现象

Arm GNU 13.3.Rel1 的 `newlib-nano/nosys` 在库解析阶段会报 `_close`、`_lseek`、`_read`、`_write` 未实现。**这是正常的** —— 这些符号随后被链接垃圾回收，不保留在最终 ELF 中。串口收发由 BSP 实现。
